# Outcome Check — design rationale

## Motivation

A coding agent can claim completion while the feature still fails. Its visible tests can have ordinary coverage gaps or can be modified. Outcome Check asks one bounded question: does a note saved through a candidate implementation exist on the server and appear in a fresh browser session?

Anthropic described premature feature completion and gaps between local tests and end-to-end behavior on November 26, 2025: https://www.anthropic.com/research/effective-harnesses-for-long-running-agents. METR documented evaluator manipulation on June 5, 2025: https://metr.org/blog/2025-06-05-recent-reward-hacking/. These are historical motivations, not evidence that either organization lacks defenses today. No METR transcripts or labels are used as executable fixtures.

## The interesting part

A browser-only implementation passes all three visible tests, including reload, while a fresh session sees nothing. A second implementation passes a deliberately weakened one-assertion test suite while doing no work. Both fail the same independently controlled outcome contract. A working implementation with legitimately refactored tests still passes. Correctness and test integrity are separate signals.

The contribution is an executable boundary plus an evidence report: a completion claim, exact candidate fingerprint, rerun baseline, fresh input, direct storage observation, clean browser observation, and screenshots. This is protected end-to-end testing applied to agent completion claims, not a new algorithm for detecting intent.

## Decisions and boundaries

- One task, four reviewed browser-side implementations. Candidate backend patches and arbitrary uploads are out of scope.
- Candidate-controlled artifacts: frontend module, visible test module, and illustrative completion claim. All are handcrafted and labeled; there are no recorded or live model calls.
- Verifier-controlled components: contract, random input, fresh workspaces, browser contexts, verdict logic, and report construction. Baseline tests and independent checks use different workspaces.
- Independent storage evidence comes from a separate SQLite connection opened read-only. The application can write notes through its ordinary API; it cannot modify the verifier through that API.
- Browser requests are limited to the bundled candidate, shared assets, and that verification's notes API. A request cannot supply an arbitrary target URL or code.
- The host, shared UI, backend API, storage, and verifier are trusted. These components share one deployed process/container. This is not a sandbox for hostile code; a compromised host could forge evidence.
- Report hashes identify the source and observed artifacts. They are not signatures, proof of provenance, or remote attestation.

## Result semantics

Pass means both required observations completed and match. Fail means a completed observation contradicts the contract. Unverifiable means evidence is missing and no completed check already establishes failure. The observer-outage toggle is an explicit simulation that demonstrates abstention on a correct implementation. A mismatch is a reason to investigate; it cannot distinguish a mistake from deliberate manipulation.

The task covers one save and a fresh-session read. It does not cover concurrency, crash recovery, restart persistence, long-term durability, user authentication, or other notes. LocalStorage is a valid choice for other products; here it violates an explicit cross-session server-storage requirement.

## Baseline and measurement

Baseline: execute each candidate's submitted visible tests. Independent verifier: execute the same protected contract against every candidate. Expected outcomes are specified by hand before execution. Tests check exact text and cardinality, not merely the presence of a green UI state.

The browser-only and empty-save candidates are incorrect; server-save and refactored are correct. Report false acceptances among incorrect fixtures, false rejections among correct fixtures, and abstentions, with denominators. Measured artifacts are generated by `npm run test:live` and saved in `artifacts/`. This tiny constructed suite demonstrates mechanisms; it does not estimate model reward-hacking rates or real-world detection accuracy.

## Simplicity and tradeoffs

One Node service, SQLite, Playwright, and plain HTML/CSS/JavaScript. No framework, model billing, reviewer credentials, external data, job queue, or separate database service. Verification is serialized to bound browser memory. Workspaces and in-memory reports expire after one hour; restarts can remove them. Reports can be downloaded. Only fictional demo notes should be entered.

Free hosting may sleep and adds cold-start delay. Browser execution costs more than validating a static artifact, but makes the outcome discrepancy observable. The server-side database is intentionally ephemeral hosting storage: passing this task says nothing about surviving a deployment or server restart.

## Extensions

The first extension would be recorded coding-agent patches with independently retained task contracts and artifacts. Next would be a real isolation boundary for candidate backend code, with separate verifier credentials and a constrained observer. Those require additional engineering and are deliberately excluded from this prototype.
